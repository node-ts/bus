# bus-cli

The `bus` command line. Read the root `CLAUDE.md` first.

- `bus.mjs` is the bin. It's committed outside `dist` (and `bin/` is gitignored) so pnpm links it into the workspace before the package is built. It only calls `runCli` from `dist/cli.js`. Add commands to `COMMANDS` in `src/cli.ts`, one folder per command (#283 and #269 add more).
- `generate-message-types` reads the project with the TypeScript compiler API, read-only, using the **project's** `typescript` (a peer dependency, loaded by `load-type-script.ts` from `cwd`), so its defaults match the user's build. Only `import type` TypeScript in the source and take enums like `ts.TypeFlags` from the loaded module, since their values differ between versions. The out file is replaced by a stub in the compiler host, so a project that imports it type checks before the file exists. Syntax errors and the unresolved-name/module codes in `BLOCKING_DIAGNOSTIC_CODES` stop generation; other semantic errors are returned as `warnings`. `MessageTypeReader` walks the exports declared in the entry files (re-exports are skipped): non-abstract classes with a `$name`, `defineCommand`/`defineEvent` definitions (recognised by shape: callable, with a `NAME`, returning a type with `$name`), and, after every file, interfaces and type aliases with a literal `$name` that don't just describe a message already read. It records only the fields that need restoring. Every other declaration with a `$name` is pushed onto `warnings` with the reason (unexported, abstract, unset, non-literal, generic, shadowed by a class, a definition inside an exported object, an inherited static `NAME`, re-exported from a non-entry file). `export default` definitions are read, keyed `#default`. A class whose static `NAME` isn't its `$name` is a problem. Anything it can't describe is pushed onto `problems` rather than thrown, so one run reports every problem. `message-types-model.ts` must stay in step with `MessageFieldType`/`MessageTypes` in `@node-ts/bus-messages` and the reviver in `bus-core/src/serialization/message-type-reviver.ts`.
- `provision` (`src/provision/`): `loadBusConfiguration` imports the module with Node's own `import()` (kept as a real dynamic import in the CJS build, so ESM, CJS and type-strippable TypeScript all load), reads the export (falling back to a CommonJS module's `default` object for named exports), calls it if it's a function, and recognises a `BusConfiguration` by shape (a `build` function), or else a built, uninitialized `BusInstance` (a `provision` function, for framework integrations such as bus-nestjs' `createBusForProvisioning`), since the module may use another copy of bus-core. bus-core is only a devDependency, used for types. `runProvision` builds (unless given a bus), calls `bus.provision({ dryRun })` and always disposes. `bus.mjs` exits explicitly once stdout and stderr are flushed, since a loaded app may leave handles open. Output is `formatProvisionReport` or the JSON `ProvisionReport` (exported; `formatVersion: 1`, only ever add fields; `runtimePermissions` only with `--permissions`). Exit codes: 0, 1 (load/provision failure), 2 (usage). `run-provision.spec.ts` injects a fake importer; `run-provision.integration.ts` runs `bus.mjs` on `test/provision/bus.ts` (its own `type: module` package.json, type stripped by Node).
- Type keys are `<package name>/<module path>#<Name>` (the package is the nearest `package.json` above the tsconfig), so two declarations with the same name, in one library or two, never collide. Anonymous object types are keyed by the field they're in (`…#Order.meta`). Fields typed as an abstract class are a problem, since the subclass can't be told apart.
- The generated file sets `source` (package + out path, named in `MessageTypesConflict`) and only exports `messageTypes`, with no side effects: users pass it to `Bus.configure().withMessageTypes()`, and nothing is registered globally. The generator warns when nothing in the program imports the out file (the stub is only in the program if something imports it), since it then can't reach a bus. `--entry` files are added to the program even if the tsconfig leaves them out, e.g. adapters' `test/` fixtures, and `rootDir` is ignored.
- `writeMessageTypes` emits the file. Imports end in `.js` under `node16`/`nodenext` module resolution, and have no extension otherwise. Import names are the export names, made unique (`Address_2`) and kept clear of the names the file declares.
- `--check` and regeneration compare files with `isSameMessageTypes`, which ignores formatting, quotes and import order, so formatters can touch the generated file.
- Tests: `src/generate-message-types/generate-message-types.spec.ts` runs against the fixture projects in `test/` (each with its own tsconfig and package.json): `supported`, `unsupported`, `skipped` (every warning for a skipped `$name`), `same-names` (one name in several modules), `two-libraries`, `imports-generated` (first run with the out file imported) and `non-strict`. `run-generate-message-types.integration.ts` copies `test/supported` into `tmp/` (gitignored, inside the package so `@node-ts/bus-messages` resolves), runs the CLI, type-checks the result, transpiles it file by file and round trips a message through `JsonSerializer`.
