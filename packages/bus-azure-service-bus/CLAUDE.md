# bus-azure-service-bus

An Azure Service Bus transport (`@azure/service-bus` 7.10+). Read the root `CLAUDE.md` first.

## Design

- **Config** (`src/azure-service-bus-transport-configuration.ts`): `queueName`, `deadLetterQueueName` (default core's `dead-letter`), `connectionString` or `fullyQualifiedNamespace` + `credential` (a `TokenCredential`; there's no `@azure/identity` dependency), `lockDuration` (`PT1M`), `maxAutoLockRenewalDurationInMs` (5 min), `maxDeliveryCount` (10), `resolveTopicName`, `verifySubscriptions` (false). The constructor takes an optional `ServiceBusClient` and `ServiceBusAdministrationClient`; the transport only closes a client it created (`ownsClient`). Without config or clients, `connect()`/`provision()` throw `AzureServiceBusConnectionNotConfigured`.
- **Topology**: a topic per message (`resolveTopicName` in `src/entity-names.ts`: drop a leading `@`, characters outside `[a-zA-Z0-9._-]` become `-`, over 260 chars shortened with an 8-hex sha256 suffix). One queue per endpoint. On each handled topic and each external custom-handler topic, a subscription named `resolveSubscriptionName(queueName)` (50 chars max, same hashing) with `forwardTo` the queue and `forwardDeadLetteredMessagesTo` the DLQ; it keeps the default `$Default` (1=1) rule. A receiver can't be created on a forwarding subscription.
- **Lifecycle**:
  - `connect` stores `concurrency` and creates the client. `start` creates a peek-lock receiver (`skipParsingBodyAsJson`, auto lock renewal) and `subscribe()`s with `maxConcurrentCalls = concurrency` and `autoCompleteMessages: false`. Each `processMessage` pushes the message into `receivedMessages` and waits on its entry in `settlements` until `deleteMessage`/`returnMessage`/`fail` settles it (`settle()`), so at most `concurrency` messages are held. The SDK doesn't allow concurrent `receiveMessages` calls on one receiver, which is why it's push-based.
  - `stop` (which the bus calls before its workers finish) releases waiting reads, suspends the subscription and abandons unread messages; the receiver stays open so in-flight messages can still settle. `disconnect` closes the receiver, senders and an owned client.
  - `provision` (deploy time or `withAutoProvision()`): `getNamespaceProperties()` (Basic tier → `AzureServiceBusTierNotSupported`), topics, then the DLQ, then the service queue (a forwarding target must exist first), then subscriptions. 409 counts as success; then the queue's `lockDuration`/`maxDeliveryCount`/`forwardDeadLetteredMessagesTo` and the subscription's `forwardTo`/`forwardDeadLetteredMessagesTo` are compared (`settingsDiffer`: forward targets by last URL segment, case-insensitively) and updated if they differ. A dry run makes no calls. The plan's `runtimePermissions` is `azure-rbac`: `{ roleAssignments: [{ role, roleDefinitionId, scope }] }`, scopes relative to the namespace resource id (`/queues/<q>`, `/topics/<t>`, `''` = namespace for `sendsAnyMessage`): Data Receiver + Data Sender on the queue, Data Sender per topic, Data Owner on the DLQ and subscribed topics with `verifySubscriptions`.
  - `initialize` creates nothing, and checks nothing when send-only or `verifyResources` is off. Otherwise it peeks the service queue (Listen only; `MessagingEntityNotFound` = missing), and with `verifySubscriptions` checks the DLQ, topics and subscriptions through the admin client. Missing ones go in one `ResourcesNotProvisioned`. Publishing to a missing topic throws `ResourcesNotProvisioned`; only with `autoProvision` does `publishMessage` create a topic it hasn't seen (`knownTopics`).
- **Messages**: the body is the serialized message as a UTF-8 `Buffer` with `contentType: application/json` (read back from bytes, a string, or JSON of an object another client sent). Native `messageId` = bus `messageId`, `correlationId`, `replyTo`, `subject` = `$name`. Application properties (`src/message-properties.ts`): headers under their own names, `attributes.<k>`, `stickyAttributes.<k>` (types kept, `undefined` dropped), `messageId`, `sentAt`, plus `failedAttempts` on retry copies. Reserved header names: `messageId`, `sentAt`, `failedAttempts`, `bus-failure`, `DeadLetterReason`, `DeadLetterErrorDescription`, `attributes.*`, `stickyAttributes.*`. `TransportMessage.id` is the native id.
- `returnAddress` is unset, so it's `endpointName`. `sendToAddress` sends to the queue by name in the same namespace and maps `MessagingEntityNotFound` to `EndpointNotFound`. A send that fails with `MessageSizeExceeded` throws `AzureServiceBusMessageTooLarge`. Senders are cached per entity and dropped when the entity is missing.

## Retry and failure

- `returnMessage(message, delay)` schedules a copy on the service queue at now + delay (`scheduleMessages`, or `sendMessages` for 0), with `failedAttempts` + 1 and native id `<bus messageId>:<attempt>` (`toRetryCopy`), then completes the original. Schedule first, so a failed complete means a duplicate, not a loss. `failedAttempts` comes only from that property, never `deliveryCount` (abandoning unread messages at shutdown bumps it).
- `fail(message, failure)` uses native `deadLetterMessage` with `deadLetterReason` = error name, `deadLetterErrorDescription` = error message, `bus-failure` = `toFailureHeader(failure)` and `failedAttempts: 0`. The queue's `forwardDeadLetteredMessagesTo` moves it, with its properties, to the shared DLQ (verified on the emulator), so no runtime permission on the DLQ is needed. Unparseable messages go the same way. `maxDeliveryCount` dead-letters (no `bus-failure`) only catch crash loops.

## Tests

- Integration tests need the emulator: `docker compose --profile azure-service-bus up -d` from the repo root, then wait for `curl localhost:5300/health`. Clients come from `src/test/service-bus-emulator.ts` (AMQP on 5673, management on 5300, overridable with `SERVICE_BUS_EMULATOR_*`). The admin client only works against the emulator from `@azure/service-bus` 7.10, which uses HTTP when the connection string has `UseDevelopmentEmulator=true`.
- Emulator limits: 50 queues + topics, 10 connections (one per `ServiceBusClient`, so tests share one), 256 KB messages, 1 h TTL, `maxDeliveryCount` 1-10, lock at least 5 s, nothing survives a restart, and `getQueueRuntimeProperties` doesn't parse. The suite deletes every entity before and after it runs (`deleteAllEntities`), and each describe deletes its own.
