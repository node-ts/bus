Add a durable transactional outbox (#260). `Bus.configure().withOutbox()` handles each message in one transaction of the persistence, which every handler of the message shares: the workflow state they save, the data they write with the persistence's accessor and the messages they send are kept together, or not at all. The messages are stored in the outgoing messages table in the transaction, sent straight away once it's committed, and deleted once sent. One the transport fails to send, or takes more than 10 seconds to send, stays in the table and is sent by a started bus that uses the same persistence, as delayed messages are, so it's never lost and the message being handled isn't retried. A handler that fails, or calls `failMessage()` or `returnMessage()`, rolls the transaction back, so its retry doesn't repeat what the other handlers sent or start a second workflow instance. The transaction is always rolled back if it isn't committed, such as when a message can't be converted to store it. Delivery is at least once.

- `OutgoingContext.dispatched` settles when the transaction is committed: resolved for every message kept, since a started bus sends it if it can't be sent straight away, or rejected with `OutgoingMessageDropped` as `duplicate`, or with the new reasons `transaction-failed` (storing or committing failed) and `transaction-work-failed` (work given to `bus.transaction()` threw). `@node-ts/bus-opentelemetry` counts an outbox message as sent at the commit, and only delayed ones as scheduled.
- `bus.transaction(async ctx => ...)` runs work outside a handler, such as in an HTTP API, in a transaction whose messages are sent once it's committed. Inside a handler it joins the handler's transaction, and if the work throws, the whole transaction is rolled back, even if the error is caught, and the message fails with the new `TransactionRolledBack`. It throws `OutboxNotEnabled` without `withOutbox()`.
- `HandlerContext` has an optional `transaction`, the persistence's transaction typed `unknown`, which workflow handlers and handler middleware get too.
- `Persistence` has an optional `beginTransaction()`, returning a `PersistenceTransaction`. `build()` throws `OutboxNotSupported` for `withOutbox()` with a persistence that doesn't implement it and the outgoing message methods, such as `MongodbPersistence` until #323. `InMemoryPersistence` implements it, holding a transaction's changes until it's committed, and throws the new `OutgoingMessageStoredConcurrently` from `commit()` when another transaction stored a message with the same id first, so the message is retried.
- `PostgresPersistence` implements it on a client checked out of the pool, held until the transaction ends. `postgresTransaction(ctx)` returns the `query` of that client, so handlers write their own data in the transaction. Its `query` throws `TransactionNotActive` once the transaction has ended, and `TransactionNotActive` now has a `reason`: no transaction, another persistence's, or ended. A commit that Postgres turns into a rollback, because a statement failed even though a handler caught the error, throws `TransactionRolledBack`, so the message is retried rather than deleted with none of its writes kept. `postgresTestTransaction(client)` wraps a fake client, so a handler that uses `postgresTransaction(ctx)` can be unit tested with a fake context.
- `OutgoingMessage.leaseUntil`, a time by the bus' clock, is replaced by `leaseMs`, which a store adds to its own clock, as claims compare with it.
- Replies from `ctx.reply()` are stored too, as `OutgoingMessage`s of the new `kind` `reply` with the address they're sent to in the new `destination`, and a bus sends a stored reply with `Transport.sendToAddress`. A store must keep `destination`: `InMemoryPersistence` and `MongodbPersistence` do, and `PostgresPersistence` stores it in a nullable `destination` column of `outgoing_messages`. A stored reply returned without one fails to send with `OutgoingMessageDestinationMissing`, whose help says to delete it.
- A bus with `withOutbox()` that never sends stored messages itself (send-only, a receiver or dispatching off) warns at `initialize()` when its persistence isn't durable or shared with another bus, since a message it fails to send would be lost.
- `@node-ts/bus-test` adds `outboxTests(persistence)`, which checks a persistence keeps the outbox's guarantees, and `scheduledMessageRoundTripTests` checks a stored reply keeps its `destination` and a stored lease runs on the store's clock.

**Breaking:** without `withOutbox()`, the handlers of a message now share one outbox in memory. The workflow state they save and the messages they send are held until they all resolve, and dropped if any of them fails. The workflow state is then saved, checking its version, before the messages are sent, so a state saved elsewhere since it was read fails the message. They used to be saved and sent as each handler resolved, so a retry after another handler failed sent the messages again, or skipped them when a workflow guarded on state it had already saved. When several workflows handle one message and one's state can't be saved after another's was, the messages of the workflow whose state was saved are still sent before the retry, so they're delivered at least once rather than lost; use `withOutbox()` when several workflows handle one message. A handler whose messages must go out whatever its siblings do needs a message of its own, and handler middleware no longer sees the state saved when `next()` resolves.
